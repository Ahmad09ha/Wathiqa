# خطة بناء الـ MVP — وثيقة (Wathiqa) لإدارة ملفات استيراد الخيوط

> كيف تستخدم هالملف: امشي فيه بالترتيب. كل خطوة فيها **شو نسوي**، **ليش**، و**كيف نتأكد إنها خلصت**.
> إذا اختلفت مع قرار، اقرأ "ليش" قبل ما تغيّره، لأنو أغلب القرارات هون هدفها تتجنّب إعادة كتابة مكلفة لاحقاً.

---

## 0. الصورة الكبيرة بثلاثة أسطر

1. المشروع الحالي هو **محرر قوالب مستندات** (جدولين: `Template` و`Document`، والمحتوى JSON). الـ MVP الجديد **نظام بيانات علائقي**: شركات، طلبات، دفعات، بوالص، حاويات، تخليص، مستندات.
2. منحتفظ بالـ stack (.NET 9 + EF Core + PostgreSQL + Next.js) وبواجهة الـ RTL العربية، ومنبدّل **نموذج البيانات** بالكامل.
3. الـ PDF بالـ MVP **مرفق مرجعي** بيظهر جنب الفورم. الاستخراج التلقائي (استخراج ثم مراجعة ثم اعتماد) بيجي **بعد** ما يشتغل الأساس.

## 1. شو الـ MVP وشو مو MVP

### تعريف النجاح

الـ MVP ناجح إذا أدخلت **5 طلبات حقيقية** (من شغل ألوان تكس مثلاً) وقدرت تجاوب هالأسئلة **بدون Excel**:

1. كم باقي علي دفع لكل مورّد؟ (حسب العملة)
2. شو الطلبات اللي وصلت ولسا ما انسددت بالكامل؟
3. شو الحاويات اللي هلق بالبحر؟
4. وين بوليصة الطلب فلان، وشو المستندات الناقصة فيه؟
5. شو حالة التخليص الجمركي لكل شحنة؟

### يدخل بالـ MVP

| البند | ليش |
|---|---|
| تسجيل دخول + عزل بيانات كل تاجر (Multi-tenant) | بدونها ما بتقدر تعطي النظام لتاجر ثاني. وإضافتها لاحقاً بتعني تعديل كل استعلام |
| الشركات (مورّد / مخلّص / شركة شحن / عميل) | كل الفلاتر مبنية عليها |
| الطلبات + البنود | القلب الرئيسي |
| الدفعات (مخططة وفعلية) | فلتر "شو باقي علي" |
| الشحنات (بوليصة) + الحاويات | فلتر "شو وصل وشو ما وصل" |
| التخليص الجمركي (حالة + بيان + مخلّص) | مطلوب منك صراحة |
| رفع المستندات وربطها بالطلب أو البوليصة أو الحاوية | "احفظ المعلومات والبوالص" |
| قائمة الطلبات مع الفلاتر | هاد الشي اللي التاجر رح يستعمله كل يوم |
| لوحة تحكم بسيطة | أرقام تطمّن المستخدم إنو النظام شغّال |

### ما يدخل بالـ MVP (مؤجّل عن قصد)

| البند | ليش مؤجّل |
|---|---|
| استخراج بيانات من الـ PDF | محتاج نموذج بيانات ثابت أولاً، وكل خطأ بالاستخراج بيتعالج بمراجعة بشرية، فلازم تكون الشاشات اليدوية جاهزة |
| OCR للملفات الممسوحة | خدمة منفصلة ومعقّدة، وبتزيد التكلفة |
| التنبيهات (إيميل/واتساب) | محتاجة بيانات حقيقية تتراكم أولاً |
| التكلفة النهائية (Landed Cost) والتقارير | بتعتمد على اكتمال إدخال المصاريف |
| أسعار صرف وتحويل عملات | بالـ MVP الدفعات بعملة الطلب (غالباً USD) |
| عروض محفوظة (Saved Views)، تصدير Excel/PDF | تحسينات، مو أساس |
| تطبيق جوال | الواجهة المتجاوبة كافية |

## 2. القرارات الأساسية وأسبابها

### D1. جداول علائقية بدل JSON

**القرار:** كل معلومة بعمود حقيقي (`Amount`, `Status`, `SupplierId`...). منوقف استعمال `ContentJson` كمخزن رئيسي.

**ليش:** الفلاتر والمجاميع ("المتبقي لكل مورّد"، "الطلبات المتأخرة") بتحتاج `WHERE` و`GROUP BY` و`SUM`. على JSON هالشي بطيء ومعقّد وبيتكسر بسهولة. القاعدة العلائقية بتضمن كمان إنو ما في دفعة معلّقة بالفراغ بدون طلب.

### D2. التسلسل: طلب ← شحنة (بوليصة) ← حاوية

```
الطلب (Order / PO)
 ├─ البنود (OrderItems)        ← شو اشتريت وبأي مواصفات
 ├─ الدفعات (Payments)         ← شو دفعت وشو باقي
 └─ الشحنة (Shipment = B/L)
     ├─ الحاويات (Containers)  ← كل حاوية لها رقم وحالة وصول
     └─ التخليص (CustomsClearance)
```

**ليش:** الطلب الواحد ممكن ينقسم لأكتر من بوليصة (شحن جزئي)، والبوليصة الواحدة ممكن تغطي أكتر من حاوية. لو دمجت المستويات بتضطر تكرّر البيانات أو تفقد دقة "2 من 3 حاويات وصلت".

### D3. الدفع على الطلب، والوصول على الحاوية، والتخليص على البوليصة

**ليش:** هيك الواقع: الدفعات بتكون على الطلب أو الفاتورة، الحاويات بتوصل لحالها وبتواريخ مختلفة، والبيان الجمركي غالباً بالبوليصة.

### D4. ثلاث حالات منفصلة (دفع / وصول / تخليص) + حالة إدارية

- `PaymentStatus`: غير مدفوع / جزئي / مدفوع.
- `IsPaymentOverdue`: **علامة منفصلة** (true/false) مو حالة رابعة.
- `ArrivalStatus`: لم تُشحن / بالبحر / بالميناء / وصول جزئي / مستلمة.
- `ClearanceStatus`: لم يبدأ / مستندات ناقصة / قيد الفحص / دُفعت الرسوم / مُفرج عنها.
- `Status` (إداري): مسودة / مؤكد / مغلق / ملغى.

**ليش علامة التأخير منفصلة:** الطلب ممكن يكون "مدفوع جزئياً" و"متأخر" بنفس الوقت. لو خلّيتها حالة وحدة، بتفقد وحدة منهم بالفلتر. (هاد تعديل بسيط على اللي اقترحته قبل: كنت حاطّ "متأخرة" كحالة دفع.)

### D5. الحالات المشتقّة بتتخزّن بالقاعدة لكن **ما حدا بيعدّلها يدوياً**

المستخدم ما بيختار "مدفوع". النظام بيحسبها من الدفعات والحاويات وبيخزّن النتيجة بأعمدة بجدول `Order` بنفس العملية (Transaction).

**ليش خزّنها ولا احسبها وقت الاستعلام؟**
- تخزينها = فلاتر سريعة وترتيب وفهارس بسيطة، وهاد مهم لما يصير عندك آلاف الطلبات.
- منعها من التعديل اليدوي = ما في تناقض بين "الدفعات" و"الحالة".
- مكان واحد بالكود بيحسبها (`OrderStatusCalculator`) = إذا تغيّرت القاعدة، بتغيّرها بمكان واحد.

### D6. المبالغ بـ `decimal`، والكمية بالكيلوغرام دائماً

**ليش:** `double` بيعطي أخطاء تقريب بالأموال. وإذا خزّنت مرة بالطن ومرة بالكيلو بتتلخبط المجاميع. المستخدم ممكن يدخل بالطن، والنظام بيحوّل ويخزّن كغ.

### D7. المستندات: ملف واحد، وروابط متعددة

الملف بيتخزّن مرة وحدة، وجدول `DocumentLink` بيربطه بطلب أو بوليصة أو حاوية (أو أكتر من وحدة).

**ليش:** بوليصة وحدة لـ 3 حاويات ما لازم تنرفع 3 مرات.

### D8. المستندات خارج قاعدة البيانات

الملفات على القرص (أو S3 لاحقاً)، وبالقاعدة بس المسار والبيانات الوصفية. وراء واجهة (`IFileStore`) حتى يتبدّل التخزين بدون ما يتأثر باقي الكود.

**ليش:** حجم القاعدة بيكبر بسرعة وبتصير النسخ الاحتياطية بطيئة، وملفات PDF الكبيرة مكانها مو Postgres.

### D9. نبقى على .NET وPostgreSQL وNext.js

**ليش:** الكود الحالي والبنية والاختبارات جاهزين وشغّالين. تبديل اللغة هلق = وقت ضايع بدون قيمة للمستخدم. قرارك بالـ stack بيهم أقل بكتير من إنك توصل لتاجر حقيقي بسرعة.

## 4. الخطوات بالترتيب

حجم كل خطوة تقريبي: **S** صغيرة، **M** متوسطة، **L** كبيرة. الوقت الفعلي بيعتمد على ساعاتك، فما رح حط تواريخ.

### الخطوة 0 — تجهيز المشروع (S)

**شو نسوي:**
1. افتح فرع Git جديد (مثلاً `mvp-shipments`). ما تمسح شي من `main`.
2. **احتفظ بـ:** هيكل الواجهة العربية (`layout.tsx`, `globals.css`, `BrandMark`, `ToastProvider`, `ConfirmDialog`, `SmoothScroll`)، سكربتات التشغيل (`start.ps1`...)، نمط السكربتات الاختبارية، وكود استيراد الـ PDF (`PdfPig`) لأنو رح نحتاجه بالمرحلة 2.
3. **جمّد (لا تحذف بعد):** محرر Tiptap، القوالب، `Seed.cs`، `ContentTools.cs`، تصدير Excel للمستندات. بعد ما يشتغل الـ MVP بتحذفهم.

**ليش:** بدك بدايات نظيفة بدون ما تخسر شغلك. والحذف المتأخر أسلم من الحذف المبكر، لأنو أحياناً بتحتاج ترجع لكود قديم تقتبس منه.

**تحقق:** المشروع بيبني (`dotnet build`) والواجهة بتفتح على الفرع الجديد.

---

### الخطوة 1 — تسجيل الدخول وعزل التجار (M)

**شو نسوي:**
1. استخدم **ASP.NET Core Identity** (جاهز ومجرّب) بدل ما تكتب تسجيل دخول بإيدك. الـ README نفسه بيقول إنو ما في مصادقة.
2. جدول `Tenant`، وكل مستخدم عنده `TenantId` ودور (`Admin` أو `Staff`).
3. واجهة بسيطة: `/login`، وخروج.
4. **فلتر عام بـ EF Core** بيضيف `TenantId` تلقائياً لكل استعلام:

```csharp
public interface ITenantOwned { Guid TenantId { get; set; } }

// داخل DbContext، والـ _tenantId جاي من المستخدم المسجّل دخوله
modelBuilder.Entity<Order>()
    .HasQueryFilter(o => o.TenantId == _tenantId && !o.IsDeleted);
// كرر نفس الشي لكل كيان فيه TenantId
```

5. عند الحفظ، `SaveChanges` بيعبّي `TenantId` وحقول `CreatedBy/UpdatedBy` تلقائياً.

**ليش أول خطوة:** لو بنيت الشاشات بدون عزل وبعدين أضفته، لازم تراجع كل استعلام وكل endpoint. ونسيان وحدة = تاجر بيشوف بيانات تاجر ثاني. بنفس الوقت الفلتر العام بيخلّي هالخطأ شبه مستحيل.

**الأدوار:** اثنين بس بالـ MVP (`Admin`, `Staff`). الأدوار التفصيلية (محاسب، مخلّص...) بتجي لما تعرف فعلاً مين بيعمل شو.

**تحقق (إلزامي):** اختبار آلي: تاجران A وB. A بينشئ شركة. B بيطلب قائمة الشركات وما بيشوفها، وبيطلبها بالـ Id مباشرة (`GET /api/companies/{id}`) وبيرجع 404.

---

### الخطوة 2 — Migrations وكيان أساسي (S)

**شو نسوي:**
1. استبدل `EnsureCreated` بـ **EF Core Migrations**.
2. كلاس أساسي `BaseEntity` فيه الحقول المشتركة (Id, TenantId, تدقيق, IsDeleted).
3. **الحذف الناعم:** `IsDeleted` بدل `DELETE`، والفلتر العام بيخفيه تلقائياً.
4. ضبط الدقة: `HasPrecision(18, 4)` للمبالغ، `HasPrecision(18, 3)` للكميات.
5. خزّن الـ enums كنص (`HasConversion<string>()`).

**ليش:** `EnsureCreated` ما بيعدّل جدول موجود، فأي تغيير بالأعمدة بعد ما تدخل بيانات حقيقية بيضطرك تمسح القاعدة. والمايغريشنز هي طريقة تطوّر القاعدة بدون ما تفقد شي. والحذف الناعم مهم لأنو حذف دفعة أو شحنة بالغلط بدون رجعة = كارثة بالمجال المالي. والـ enums كنص بتخلّي قراءة القاعدة مباشرة ممكنة.

**تحقق:** `dotnet ef database update` على قاعدة فاضية بينشئ كل شي، وإضافة عمود تجريبي ثم migration جديد بتشتغل بدون مسح البيانات.

---

### الخطوة 3 — الشركات (S)

**شو نسوي:**
- API: قائمة (بحث بالاسم + فلتر النوع + ترقيم صفحات)، إنشاء، تعديل، حذف ناعم.
- واجهة: جدول، فورم، صفحة تفاصيل (بالبداية بدون الإحصائيات).

**ليش بالبداية:** هي أبسط CRUD، فبتتأكد إنو الأساسات (Auth + Tenant + Migrations + الواجهة) كلها شغّالة. وأي خلل بيبين هون وهو رخيص الإصلاح، مو بعد ما تبني فوقه 5 شاشات.

**تحقق:** أنشئ مورّد، مخلّص، وشركة شحن. حاول حذف مورّد عليه طلبات (لما نبني الطلبات) وتأكد إنو النظام بيمنعك أو بيحذف حذفاً ناعماً بدون ما يكسر الطلبات.

### الخطوة 4 — الطلبات والبنود والترقيم (M)

**شو نسوي:**
1. `Order` + `OrderItem` مع CRUD. الحفظ بيتم بطلب واحد (الطلب وبنوده معاً).
2. **الترقيم التلقائي** `PO-2026-0001` عبر `NumberSequence`: داخل Transaction بتقفل الصف (`SELECT ... FOR UPDATE`) وبتزيد الرقم.
3. حساب `LineTotal` بالسيرفر:
   - الكمية دائماً بالكغ. إذا كانت `PriceUnit = TON` فالإجمالي = `QuantityKg / 1000 × UnitPrice`.
   - قاعدة تقريب واحدة بكل مكان: خانتين عشريتين، `MidpointRounding.AwayFromZero`.
4. `TotalAmount` = مجموع `LineTotal`، بيتخزّن بالطلب.
5. تحقق من الإدخال: كمية > 0، سعر ≥ 0، عملة من قائمة معروفة.

**ليش الترقيم داخل Transaction:** لو شخصين أنشأوا طلب بنفس اللحظة، بدون قفل ممكن ياخدوا نفس الرقم. والرقم المكرر بالمجال التجاري مشكلة مزعجة جداً.

**ليش السيرفر يحسب مو الواجهة:** الواجهة ممكن تتلاعب أو تغلط، والـ API ممكن يُستدعى من أماكن ثانية لاحقاً. السيرفر هو الحَكَم.

**تحقق:** طلب فيه بندين (واحد بالكغ وواحد بالطن). تأكد إنو `TotalAmount` صح بحسبة يدوية.

### الخطوة 5 — الدفعات والحالات المشتقّة (M) ⭐ أهم خطوة منطقياً

**شو نسوي:**
1. CRUD للدفعات داخل تاب "الدفعات" بصفحة الطلب. المخططة (بدون `PaidDate`) والفعلية بنفس الجدول.
2. اعمل كلاس واحد `OrderStatusCalculator`. بعد **أي** تعديل على بنود/دفعات/حاويات/تخليص، استدعيه داخل نفس الـ Transaction لتحديث أعمدة الطلب:

```csharp
public static PaymentStatus Payment(decimal total, IReadOnlyCollection<Payment> payments)
{
    var paid = payments.Where(p => p.PaidDate != null).Sum(p => p.Amount);
    if (total > 0 && paid >= total) return PaymentStatus.Paid;
    return paid > 0 ? PaymentStatus.Partial : PaymentStatus.Unpaid;
}

public static bool IsOverdue(IReadOnlyCollection<Payment> payments, DateOnly today)
    => payments.Any(p => p.PaidDate == null && p.DueDate < today);
```

3. `PaidAmount` = مجموع الدفعات الفعلية. **المتبقي** = `TotalAmount - PaidAmount` (بيتحسب بالعرض، ما بحاجة عمود).
4. ما تسمح بمجموع دفعات فعلية أكبر من الإجمالي بدون تحذير واضح.
5. `AuditLog` لكل إنشاء/تعديل/حذف دفعة (مين، متى، القيمة القديمة والجديدة).

**ليش هي أهم خطوة:** كل فلاتر الدفع بتعتمد على صحة هالحساب. وإذا الحالة المخزّنة اختلفت عن الدفعات، النظام بيكذب على التاجر، وهيك بتضيع الثقة فيه. تجميع الحساب بمكان وحيد = مكان وحيد بتختبره.

**ليش تدقيق (Audit) للدفعات بالذات:** دفعة معدّلة بدون أثر = مشكلة محاسبية وخلاف مع المورّد.

**ليش الدفعة بعملة الطلب بالـ MVP:** بدون أسعار صرف ما في طريقة صحيحة لجمع عملات مختلفة. المبدأ: **لا تجمع عملتين بدون تحويل**، وبالمجاميع اعرض مجموع منفصل لكل عملة.

**تحقق (اختبارات وحدة، بدون قاعدة بيانات):**
- بدون دفعات → `Unpaid`.
- دفعة جزئية → `Partial`.
- مجموع = الإجمالي بالضبط → `Paid`.
- دفعة مخططة تاريخها أمس ولم تُدفع → `IsOverdue = true`.
- طلب بإجمالي 0 → ما بيصير `Paid` بالغلط.

### الخطوة 6 — الشحنات والحاويات وحالة الوصول (M)

**شو نسوي:**
1. تاب "الشحن" بصفحة الطلب: إضافة بوليصة (`Shipment`) وتحتها حاويات (`Container`).
2. تحقق من رقم الحاوية:
   - **أولاً:** الشكل فقط (4 حروف كبيرة + 7 أرقام).
   - **ثانياً:** رقم التحقق (ISO 6346)، ويفضّل كـ **تحذير** مو منع، لأنو أحياناً بيجي الرقم غلط من المورّد وبدك تسجّله رغم هيك.

```csharp
static int LetterValue(char c)          // A=10, B=12, C=13 ... (بتتخطى مضاعفات 11)
{
    int v = 10;
    for (char x = 'A'; x < c; x++) { v++; if (v % 11 == 0) v++; }
    return v;
}

public static bool IsValidContainerNumber(string n)
{
    if (n is not { Length: 11 }) return false;
    int sum = 0;
    for (int i = 0; i < 10; i++)
    {
        int val = char.IsLetter(n[i]) ? LetterValue(n[i]) : n[i] - '0';
        sum += val * (1 << i);          // × 2^i
    }
    int check = sum % 11 % 10;
    return check == n[10] - '0';
}
```

3. حالة كل حاوية بتتغيّر يدوياً بزر سريع (بالبحر ← بالميناء ← مستلمة) مع تسجيل التاريخ.
4. حالة وصول الطلب بتتحسب من الحاويات (داخل `OrderStatusCalculator`):

```csharp
public static ArrivalStatus Arrival(IReadOnlyCollection<Container> cs)
{
    if (cs.Count == 0) return ArrivalStatus.NotShipped;
    if (cs.All(c => c.Status == ContainerStatus.Delivered)) return ArrivalStatus.Delivered;
    if (cs.Any(c => c.Status == ContainerStatus.Delivered)) return ArrivalStatus.PartiallyDelivered;
    if (cs.Any(c => c.Status == ContainerStatus.AtPort))    return ArrivalStatus.AtPort;
    if (cs.Any(c => c.Status == ContainerStatus.AtSea))     return ArrivalStatus.AtSea;
    return ArrivalStatus.NotShipped;
}
```

5. خزّن `ContainerCount` و`DeliveredContainerCount` بالطلب، حتى القائمة تعرض "2 من 3 وصلت".

**ليش بالقائمة نعرض عدّاد:** حالة "وصول جزئي" لحالها ما بتقول للتاجر كم باقي. والعدّاد بيجاوب فوراً.

**ليش تحذير مو منع لرقم الحاوية:** النظام بيخدم المستخدم، مو بيعطّله. أخطاء المورّدين بالمستندات بتصير فعلاً، وبدك المستخدم يسجّل الواقع ويشوف التحذير.

**تحقق:** طلب بـ 3 حاويات. غيّر حالة وحدة لـ `Delivered` وتأكد إنو الطلب صار "وصول جزئي (1/3)". غيّر الباقي وتأكد إنو صار "مستلمة".

### الخطوة 7 — رفع المستندات وربطها (L)

**شو نسوي:**
1. `IFileStore` بتنفيذ أولي على القرص المحلي (مجلد **خارج** `wwwroot`).
2. endpoint رفع: `POST /api/documents` (multipart) مع: النوع + الربط (طلب / بوليصة / حاويات محددة).
3. **أمان الرفع (ما تتجاوزه):**
   - الأنواع المسموحة: PDF وJPG وPNG فقط.
   - تحقق من **أول البايتات** (magic bytes) مو من الامتداد: PDF يبدأ بـ `%PDF-`، JPG بـ `FF D8 FF`، PNG بـ `89 50 4E 47`.
   - الحد الأقصى 25 MB (الحد الحالي 10 MB ضيّق للبوالص الممسوحة).
   - الاسم المخزّن GUID عشوائي، والاسم الأصلي للعرض فقط.
   - احسب `Sha256` ونبّه إذا نفس الملف مرفوع من قبل.
4. **التحميل والعرض** عبر endpoint بيتحقق من `TenantId` قبل ما يرجّع الملف (مو مجلد ثابت). مع `X-Content-Type-Options: nosniff`.
5. واجهة: منطقة سحب وإفلات، اختيار النوع، اختيار "لأي شي": كل الطلب / بوليصة / حاويات محددة. وعارض PDF جنب الفورم (`iframe`).
6. أمثلة ذكية للتسهيل: لما النوع = B/L أو Packing List، الاقتراح الافتراضي يكون "للبوليصة"، ولما = إثبات دفع، "لدفعة".

**ليش خارج `wwwroot`:** أي ملف داخلها بيتحمّل بالرابط المباشر بدون تسجيل دخول، وهاد بيكسر عزل التجار.

**ليش magic bytes:** الامتداد بيتغيّر بثانية. ملف خبيث ممكن يُسمّى `.pdf`.

**ليش بنبني عارض الـ PDF هلق:** هو نفسه رح يصير الجهة اليمنى من شاشة "المراجعة والاعتماد" بالمرحلة 2. فبتبنيه مرة وحدة.

**تحقق:**
- ارفع بوليصة وحدة وربطها بحاويتين. تأكد إنها بتظهر بصفحة كل حاوية، وإنو ما في إلا نسخة وحدة على القرص.
- جرّب رفع ملف `.exe` مسمّى `.pdf` → لازم يرفض.
- المستخدم B ما بيقدر يحمّل ملف المستخدم A حتى لو عرف الرابط.

### الخطوة 8 — قائمة الطلبات والفلاتر (M) ⭐ الشاشة اللي رح تستعملها كل يوم

**شو نسوي:**
1. endpoint واحد بيبني الاستعلام على مراحل (`IQueryable`) حسب المعاملات:

```
GET /api/orders?supplierId=&payment=&arrival=&clearance=&overdue=true
               &from=&to=&q=&sort=&page=&pageSize=
```

2. الرد: `{ items, total, page, summaries }` حيث `summaries` = مجموع الإجمالي والمدفوع والمتبقي **مفصولين لكل عملة**.
3. الواجهة:

5. فهارس: `(TenantId, SupplierId)`, `(TenantId, PaymentStatus)`, `(TenantId, ArrivalStatus)`, `(TenantId, ClearanceStatus)`, `(TenantId, OrderDate)`.

**ليش الفلاتر بالـ URL:** المستخدم بيقدر يعمل Bookmark أو يبعت الرابط لزميله ("شوف الطلبات المتأخرة من هالمورّد")، وزر الرجوع بيشتغل منطقياً.

**ليش مجاميع منفصلة لكل عملة:** جمع 10,000 USD مع 5,000 EUR = رقم بلا معنى.

**ليش ترقيم من السيرفر:** بعد سنة بيصير عندك مئات الطلبات، وتحميلها كلها بالمتصفح بطيء.

**تحقق:** أدخل 10 طلبات بتركيبات مختلفة، وجرّب كل فلتر وتركيباتهم. مثال: "وصلت ولم تُدفع بالكامل" = `arrival=delivered&payment=unpaid,partial`.
